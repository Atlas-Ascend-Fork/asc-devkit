## Description

The header file paths are: `"simt_api/device_atomic_functions.h"` (for interfaces other than the half, half2, bfloat16\_t, and bfloat16x2\_t types), `"simt_api/asc_fp16.h"` (for the half and half2 type interfaces), and `"simt_api/asc_bf16.h"` (for the bfloat16\_t and bfloat16x2\_t type interfaces).

Performs an atomic add operation on the data in Unified Buffer (UB) or Global Memory with the specified data, that is, adds the specified data to the data in these memory regions.

## Return Value

Initial data in UB or Global Memory.

Note that due to underlying hardware constraints, the return values of the half and bfloat16\_t types are inaccurate, and directly using the return values of these types is prohibited. The half2 and bfloat16x2\_t types are not subject to this restriction.

## Constraints

-   Atomic operations guarantee the atomicity of the read-modify-write process on the same address, but do not guarantee the execution order among multiple threads. For scenarios sensitive to floating-point accumulation order, the result may vary with thread scheduling.
-   The performance of this API is affected by the following factors. For the related principles, see [Atomic Operation Mechanism](atomic_operations_intro.md#atomic-operation-mechanism). For specific performance comparison and optimization examples, see [asc_atomic_add API Performance Comparison Example](../../../../../examples/03_simt_api/02_features/01_api_features/02_atomic_operation/atomic_add_perf).
    -   Memory space: The access path of UB is shorter than that of Global Memory, and UB usually has lower access overhead. When the data type in use supports UB (that is, int32\_t, uint32\_t, float, half, bfloat16\_t, half2, bfloat16x2\_t), it is recommended to perform atomic operations in UB first.
    -   Return value: Whether the return value is used may affect the atomic add instruction generated by the compiler. The following table shows whether a better instruction can be generated for each data type when the return value is not used:

        | Data Type | Whether a better instruction is generated when the return value is not used |
        | --- | --- |
        | int32\_t, uint32\_t, float, half, bfloat16\_t, half2, bfloat16x2\_t | Yes |
        | int64\_t, uint64\_t | No |

        When the business scenario allows, it is recommended not to use the return value.
    -   Address distribution: Global Memory atomic operations are processed through the L2 Cache. The L2 Cache uses a 512B Cache Line as the cache management unit, and each Cache Line contains four 128B sectors. Global Memory atomic operations are processed at the granularity of a 128B Sector. When destination addresses are concentrated within the same Sector, the processing efficiency is lower; when destination addresses are distributed across more Sectors, the processing efficiency is higher. Therefore, when the business allows, it is recommended to distribute the destination addresses of atomic operations across more Sectors.

## Examples

See [Byte Frequency Histogram Sample](../../../../../examples/03_simt_api/03_best_practices/03_instruction_optimizations/atomic_histogram), which demonstrates in detail how to use the `asc_atomic_add()` interface to efficiently count the occurrence frequency of each byte value in an input byte sequence.

Simple example scenario: multiple threads scan a status array, where a non-zero status indicates an abnormal record. The `asc_atomic_add()` interface is used to count the number of abnormal statuses. The input parameters are described as follows:

| Name | Description |
| --- | --- |
| `status` | Each element represents a status record, where 0 indicates normal and non-zero indicates abnormal. |
| `error_count` | The abnormal counter in Global Memory, cleared to zero before kernel launch. |
| `n` | The number of input elements. |

The core code implementation is as follows:

-   SIMT programming scenario:

    ```cpp
    #include "simt_api/device_atomic_functions.h"

    __global__ __launch_bounds__(256) void count_error_status(uint32_t *error_count,
                                                         uint32_t *status,
                                                         uint32_t n)
    {
        uint32_t idx = blockIdx.x * blockDim.x + threadIdx.x;
        if (idx >= n) {
            return;
        }

        if (status[idx] != 0U) {
            asc_atomic_add(error_count, 1U);
        }
    }
    ```

-   SIMD and SIMT hybrid programming scenario:

    In SIMD and SIMT hybrid programming scenarios, address space qualifiers must be explicitly used to indicate the address space: `__gm__` indicates the Global Memory memory space, and `__ubuf__` indicates the UB memory space.

    ```cpp
    #include "simt_api/device_atomic_functions.h"

    __simt_vf__ __launch_bounds__(1024) inline void count_error_status(__gm__ uint32_t *error_count,
                                                         __gm__ uint32_t *status,
                                                         uint32_t n)
    {
        uint32_t idx = blockIdx.x * blockDim.x + threadIdx.x;
        if (idx >= n) {
            return;
        }

        if (status[idx] != 0U) {
            asc_atomic_add(error_count, 1U);
        }
    }
    ```

The output result is as follows:

```
status: 0, 2, 0, 1, 3
error_count: 3 // Indicates that 3 data items in status are non-zero.
```
